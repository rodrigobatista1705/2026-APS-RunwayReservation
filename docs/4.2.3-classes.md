# 4.2.3 Modelagem de Classes

## Dos substantivos às classes

As classes saem dos substantivos. A fonte principal é o fluxo de Registrar empréstimo, especificado na 4.2.2. Cada coisa que o ator informa ou que o sistema confirma é uma coisa que o sistema precisa lembrar. A segunda fonte é a lista de requisitos da 4.2.1. O que aparece nas duas vira classe com mais confiança.

Nem todo substantivo vira classe. Três filtros: o que é detalhe de outra coisa vira atributo (a data de devolução é do empréstimo). O que é interface não entra (tela, botão, relatório). O que está fora do sistema também não (o caderninho, o balcão).

| Substantivo | De onde veio | Vira | Por quê |
|---|---|---|---|
| usuário | passo 2, HU01, HU03. RF07 | classe **usuário da pista**| O sistema guarda quem ele é e verifica qual material esta em sua posse ou quando vai utilizar a pista |
| Responsável pela pista | ator da 4.2.2, RNF02 | atributos de **responsável** | administra o sistema e registra empréstimos |
| professor | Seção 4.1 entrevistas | especialização de **usuário** | é um tipo de usuário da pista |
| atleta | ator da 4.2.1 e entrevistas | especialização de **usuário** | utiliza os mesmos recursos que o professor |
| nome, matricula| cadastro do usuário | atributos de **usuário** | são dados de identificação |
| material esportivo | RF01, RF03, RF04, RF07 | casse **Material** | é o recurso que pode ser emprestado |
| pista de atletismo | RF03, RF04 e escopo da 4.1 | classe **pista** | pode ser reservada e consultada |
| empréstimo | RF04, RF05 e RF06 | classe **empréstimo** | registra quem está utilizando um material |
| reserva | RF04 e RF06 | classe **reserva** | registra a utilização futura da pista |

| disponibilidade | RF03 | não vira classe | representa um estado de materiais e reservas |

## Classes

O modelo possui sete classes principais. Cada uma existe porque aparece em um requisito funcional, em um fluxo de caso de uso ou no escopo definido na Seção 4.1.

Duas decisões surgiram durante a modelagem.

A primeira foi separar Reserva de Emprestimo. Embora ambos registrem utilizações, o empréstimo controla materiais esportivos enquanto a reserva controla o uso da pista. Misturar os dois conceitos faria o sistema registrar informações que não pertencem ao mesmo processo.

A segunda foi criar as especializações Professor, Atleta e Responsavel. Os três são usuários do sistema, compartilham dados de identificação e por isso herdam de uma mesma classe geral.

| Classe | Atributos | Operações | Veio de |
|---|---|---|---|
| **Usuário** | -nome: String / -matricula: String | +identificar(): boolean | RF02 e fluxo de Registrar empréstimo |
| **Professor** | herda de Usuário | nenhuma própria | ator descrito na Seção 4.1 |
| **Atleta** | herda de Usuário | nenhuma própria | HU03 e entrevista |
| **Responsável** | herda de Usuário | + registrarEmprestimo() / +cadastrarMaterial() | RNF02 e ator da 4.2.2 |
| **Material** | -codigo: String / -nome: String / -situacao: String | +estaDisponivel(): boolean | RF01, RF03 e RF07 |
| **Empréstimo** | dataEmprestimo: Data / - dataDevolucao: Data / - devolvido: boolean | +registrarDevolucao(): void | RF04, RF05 e RF06 |
| **Reserva** | - dataReserva: Data / - horarioInicio: Hora / - horarioFim: Hora |  + verificarDisponibilidade(): boolean | RF03, RF04 e RF06 |
| **Pista** | - identificacao: String / - status: String | + disponivel(): boolean | RF03 e RF04 |

A Figura 2 apresenta três tipos de relacionamentos.

As **associações** representam as relações entre usuários, empréstimos, reservas e recursos esportivos. Um usuário pode realizar vários empréstimos e várias reservas ao longo do tempo. Cada empréstimo está associado a exatamente um material. Cada reserva está associada à pista de atletismo.
A **herança** aparece entre Usuario, Professor, Atleta e Responsavel. Os três últimos representam tipos específicos de usuário e compartilham as informações de identificação definidas na classe geral.

Também existe uma associação entre Responsavel e Emprestimo, pois todo empréstimo é registrado por um responsável autorizado, conforme definido pelo RNF02.

Não há composição nem agregação no modelo atual. Nenhuma classe existe exclusivamente como parte de outra. Materiais, usuários, reservas e empréstimos possuem existência própria dentro do sistema.

## Teste de objetos

Um diagrama de classes é uma hipótese sobre como o sistema funciona. O teste consiste em representar uma situação real retirada do contexto do cliente e verificar se as classes conseguem explicá-la.

A situação escolhida foi a seguinte: uma atleta chamada Wanessa pega emprestado um conjunto de barreiras para treinamento, e o Prof. Miguel registra a operação no sistema.

| Objeto | Classe | Valores |
|---|---|---|
| "Miguel" | Responsável | nome = "Miguel", matricula = "R001" |
| "Wanessa" | Atleta | nome = "Wanessa", matricula = "A002" |
| barreira01 | Material | codigo = "MAT-01" nome = "Barreira de Atletismo", situacao = "emprestado"|
| emp01 | Empréstimo | dataEmprestimo = hoje, dataDevolucao = amanhã, devolvido = false |

**Ligações:** Miguel registra emp15 Wanessa realiza emp15 emp15 refere-se a barreira01
**O que o teste confirma**
- **Um usuário pode realizar empréstimos.** A atleta Wanessa está associada ao empréstimo
- **Todo empréstimo possui um responsável pelo registro**. O objeto Miguel está ligado ao empréstimo.
- **Cada empréstimo corresponde a um material**. O empréstimo emp15 está associado a uma única barreira.
- **O material muda de situação quando emprestado**. A barreira aparece com status "emprestado".
O teste mostra que as classes conseguem representar uma situação real descrita pelo cliente. Se algum relacionamento necessário não pudesse ser representado, o problema estaria no diagrama de classes, não nos objetos.

## Rastreabilidade com a 4.2.2

| Operação ou atributo | Classe | De onde veio |
| identificar() | Usuário | caso de uso Identificar usuário |
| registrarEmprestimo() | Responsável | caso de uso Registrar empréstimo |
| cadastrarMaterial() | Responsável | RF01 Cadastrar material |
| estaDisponivel() | Material | RF03 Consultar disponibilidade |
| registrarDevolucao() | Empréstimo | RF05 Registrar devolução |
| verificarDisponibilidade() | Reserva | RF03 Consultar disponibilidade |
| dataEmprestimo | Empréstimo | fluxo principal de Registrar empréstimo |
| dataDevolucao | Empréstimo | RF06 Consultar histórico |
| situacao | Mateial | RF07 Localizar material |
| horarioInicio, horarioFim | Reserva | registro de reservas da pista |

**Toda operação tem origem.** Nenhuma operação foi criada sem estar associada a um requisito funcional ou a um passo dos casos de uso.

**Todo requisito tem representação no modelo.** Os requisitos de cadastro, consulta, empréstimo, devolução, reserva e localização aparecem em atributos, operações ou relacionamentos entre as classes.

**O que a modelagem mudou.** Durante a modelagem tornou-se necessário separar os conceitos de Reserva e Empréstimo. Os requisitos tratam tanto da utilização da pista quanto do empréstimo de materiais, mas esses processos possuem informações diferentes e precisaram ser representados por classes distintas. Essa separação não aparecia explicitamente na 4.2.1, mas surgiu naturalmente ao transformar os requisitos em estruturas de software.
